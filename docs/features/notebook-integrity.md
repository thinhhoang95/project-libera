# Notebook check

**Notebook actions → Check Notebook…** checks a notebook against the disk and lists what is not sound, with what would set each finding right. The check only reads: nothing is repaired, moved or rewritten (that is **Try to fix**, below, and only on confirmation), and it does not load the library tree (whose upkeep prunes sidecars and writes indexes). It runs only when asked, shows which check it is on, and can be stopped.

Code: `src/lib/storage/integrity.ts` (`verifyNotebook`, `checkNothingLeftAt`), `src/app/api/notebooks/verify/route.ts`, `src/components/libera/notebook-integrity-dialog.tsx`. Tests: `scripts/editor/notebook-integrity.test.ts`, `scripts/editor/notebook-operations-integrity.test.ts`.

## One common point

The check owns no knowledge of its own. Each kind of state is asked of the module that owns it, and checked against the disk:

| Check | Asks | Finding |
|---|---|---|
| Notebook settings | `notebookMetadataPath` | settings file missing (info) or unreadable (error) |
| Side files | `listSidecars` (a folder is a file's ink folder only if it directly holds a file the ink reader accepts; stray files beside it make none), `findOrphanedSidecars`, each kind's `inspect` (sidecars.ts, from the owner: `inspectPdfSidecar`, `inspectImageSidecar`, `inspectPdfTextCache`, `inspectAudioPeaksCache`, `inspectInkFolder`, and the outline, definitions and transcript parsers), `listLegacyAnnotations` (annotations.ts: older annotation layouts, listed without upgrading them), `matchByIdentity` and `readOrphans` (pdf-sidecars.ts) | a saved side file its owner rejects, or ink files the reader leaves out (error); records its reader silently drops, which the next save loses: annotations, comments, strokes, outline entries, definitions, transcript segments (warning); side files of a file that is gone (warning), or that belong to a file moved outside the app, which they follow the next time the notebook is opened (info); a side file made for another version of its file, by size (info; for ink, only the page files whose recorded size differs, so pages drawn on the current version are not named; annotations and comments are only reported, never offered for removal); PDF text caches and waveforms out of date, one line per kind (info); ink of a page or block the file doesn't have, side files set aside for files that may come back (info); annotations still in an older layout, which the next open of the one file of that name gives them to (info), or no file has the name (info), or several do and none gets them (warning) |
| Note images and Python code | `unreferencedMarkdownAssets` (markdown-assets.ts) | Python code of a note that is gone (warning); images no note shows (info) |
| Images in notes | `markdownImageTargets` | an embedded image, Markdown or HTML `<img>`, that is missing (error). The target must be a readable file: a folder, or a link whose target is gone, is missing; a permission or drive error makes the check partial |
| Links in notes | `linkCandidates`, `resolveLinkTargetWith` (library-links.ts), `markdownHeadingAnchors`, `markdownHtmlAnchors` (markdown-link-occurrences.ts), `savedAnnotationIds` (annotations.ts), `hasUnreadableLinkPosition` | a link (inline or reference-style, a label defined twice resolving to its first definition as in CommonMark) that finds no file, resolved as the editor resolves it; a heading, in the note or another, that is not there (a real HTML `id` or `<a name>` attribute counts, in either quote style; text in code does not); a link to an annotation that is gone, including when the file has no annotation side file at all (an unreadable side file, or one only in an older layout, makes the check partial: it is not read here, since reading would upgrade it); a moment past the end of a recording, by the length its transcript or waveform saved for the recording as it is now (compared by size, like those caches; a length saved for another version leaves the position unchecked and the check partial); a saved place that can't be read, a ```chart block whose data file (`.csv`/`.tsv`, from the note's folder) is missing (all warnings) |
| LaTeX | `latexDependencies` (latex/dependencies.ts) | an `\input`/`\include`, `\includepdf`, `\lstinputlisting`, figure or bibliography that is not found from the main file's folder (error). Each main file's build is checked on its own, so a chapter two mains share is checked from each, and the finding names the build that loses the file; a folder or a dangling link is not a file, a permission or drive error makes the check partial. A name is tried as written, then with each extension TeX adds (`plot.v2` → `plot.v2.pdf`, `chap.v2` → `chap.v2.tex`). A name that needs a macro (`#1`, `\figdir/a`) is not resolved: the check says how many references it could not check (partly checked, no finding). `\usepackage` and `\documentclass` are not checked |
| Records | `inspectWorkspaceMetadata` (workspace-metadata.ts, which says when the file is damaged instead of reading it as empty), `inspectReviewKeys`, `inspectReviewDocumentProblems`, `inspectLegacyReviewKeys` (review-files.ts, lock-free), `listReviewEntryPaths`, `listRunFiles` | stars and tags of missing files, pending agent reviews of missing files (warning); review comments and undo history kept for missing files (info); a damaged stars-and-tags file (error); review comments whose document file is not on this computer, not synced yet or lost, or is there but corrupt or truncated (warning, never offered for removal, whether or not the note exists); keys of an older review database still waiting to be converted are inspected without converting it (a missing file is reported but not offered for removal, an unreadable database is a warning); unreadable review records (warning or error) |
| References | `inspectReferenceLibrary` (the app's own parser, without setting a damaged library aside), `readTetherTarget` | a reference attached to a missing file, a missing tethered `.bib` or unreadable tether settings (warning); a tether to a file outside the library whose folder is missing too is reported as possibly on a drive that is not connected, and is never offered for removal; a library the app can't read (error) |
| Indexes | `readLinkIndex` (notebook-links.ts), `readCitationIndex` (reference-citations.ts), `planBibMirror` (bib-mirror.ts, what `writeBibMirror` would do), `readIndexedLibraryPaths` (search/database.ts) | link and citation index entries whose content hash no longer matches the note (the citation index's LaTeX entries are hashed too, and a note with invalid UTF-8 is compared by its raw bytes, as the indexes hash them), notes not indexed yet, entries of files that are gone; a `.bib` mirror out of date, not written, or protected because it was edited; Global Search rows of files no longer in the notebook (all info, aggregated) |
| Migrations | `listInterruptedMigrations`, `listUnreadableMigrations` | an unfinished migration involving the notebook (error); an unreadable journal, a prepared copy left behind (warning) |

The notebook is walked once and its notes read once per check; files are checked for existence once each, and the side files are listed once. Existence is exact, as the app matches paths: each name on the way must be in its folder's listing (`readdir`, once per folder), so `Paper.pdf` is missing when the file is `paper.pdf` and a name that differs only in Unicode normalization is missing too, even where the file system would open it (stars, tags, reviews, attachments and links are matched by string against the tree, so a case-only rename in Finder loses them). Image embeds and LaTeX files are looked up on the disk as the viewer and TeX do, so those two keep the file system's own matching. Side files are compared with their file by size only (a stat), never by hashing the PDFs and recordings: a same-size change is left to the owner when the file is opened. Files are hashed only to match side files of a missing file, and only those of the size it recorded. Index entries are compared with hashes of the notes already read. Each check runs on its own: one that can't run is reported as such, and one that could only partly run (very large notebooks, unreadable notes, a folder or file it had no permission to read) says so. A path that could not be checked is never reported as missing, and says so: a star, tag, review, attachment or tether whose file can't be looked at, another library that can't be read, a same-size file that can't be read for the comparison with its side file, a note that might own some code in a folder that could not be listed, each make their check partial. **One archive scope:** the walk includes the archive (`_archive`), as Try to fix does, so an archived PDF, note or LaTeX source counts wherever it can change a verdict: where a side file went, whether Python code has an owner, whether a LaTeX project is whole. When any check is partial, the dialog says **Partly checked** instead of "No problems found".

## Try to fix: files moved outside the app

Files moved or renamed into another folder in Finder (or by a sync client) leave their records at the old path. When the check has findings that can come from that (side files, a note's Python code, records, references), the dialog offers **Try to fix…** (`src/lib/storage/repair.ts`, `src/app/api/notebooks/repair/route.ts`).

- **Plan (reads only).** The paths that records are kept for (side files, Python code, stars and tags, review comments, reference attachments in any library, the tethered `.bib`) and that are surely gone are matched to the notebook's files **by name alone**. A pair is made when exactly one missing path has that name and exactly one file has it, and that file has no records of the same kind of its own (stars and attachments don't count). An empty review, the one opening a note makes, is not the file's own: opening a moved note before the fix doesn't keep its comments from following it. Everything else is listed as left alone, with why: no file of that name, several files of that name, several missing files of that name, or the only one has records of its own. Caches never make a match; they follow a matched file.
- **Names.** A name is compared under Unicode normalization (NFC) and case-folding, so a name a sync client returns decomposed (`Bài giảng.pdf`) and a case-only rename (`Paper.pdf` to `paper.pdf`) are found; files that fold to one name are "several". A path is also missing when its exact name is not in its folder's listing, so a case-insensitive disk that answers "exists" for the old spelling does not hide the rename.
- **The archive** (`_archive`) is searched: a file moved there in Finder is a candidate, and a same-name file there counts toward "several".
- **Side files set aside.** The tree's upkeep sets side files aside (`.libera/orphaned-sidecars/`) 30 s after their file goes missing. Each set-aside record (annotations, outline, definitions, ink) is a record of its `originalPath` and is paired by the same rule. Ink records no identity of its file, so this is its only way back. A destination that already has that kind of side file makes the pair "own", as for live side files.
- **The upkeep's own reattachment** (the same bytes, or the old path back; not Try to fix) never replaces and never loses work: a side file or ink folder goes to a slot that must be free, published exclusively with the source kept until then, so one saved there meanwhile stays and the set-aside copy waits; a slot is "taken" by the file system's own case rules (on a case-sensitive volume `Foo.pdf`'s annotations do not occupy `foo.pdf`). An ink folder whose pages recorded different versions of the file is not moved or set aside as a whole; it stays where it is (Check Notebook lists it as ink of a file that is gone). An ink set-aside writes its `record.json` before moving the folder, so an interrupted one leaves a record naming the origin; a record with no folder is dropped once it is older than the 30 s grace. **Expiry:** set-aside work older than 90 days is deleted only when nothing of its file is left to come back to (no file with its bytes; with none recorded, none at the old path). A file that is back but whose slot is taken, or whose bytes match several files, keeps it for the user to decide.
- **Where a record belongs** is told by one exact-segment lookup (`fileExistence` in library-links.ts, as the check's): every name on the way, ancestors included, must be in its folder's listing. Orphan detection (`findOrphanedSidecars`) and the tree's upkeep (`reconcilePdfSidecars`, `reconcileInkFolders`) use it, so a case-only or Unicode-normalization rename of a folder above a file reads as a move on a disk whose `stat` still answers for the old spelling. Moving the side files themselves across such an alias is the reattachment's own business.
- **What upkeep matches against** is every file of the notebook, whatever the rail shows: the files of the `_archive` folders the tree hides are candidates too. When the walk did not see all of it (a folder that could not be listed, a child that raced away between listing and `stat`, a linked folder past its entry cap), upkeep does not match, set aside or expire side files that refresh, since a match among part of the files cannot be called unique; the tree carries `incomplete: true`. A folder that cannot be read shows empty and the rest of the tree still refreshes (`readTreeDirectory`, tree.ts). Entries the tree hides by name (dot folders, `_assets`, `_ink`, `node_modules` in a linked folder) are still not candidates.
- **Not planned at all** when a folder of the notebook could not be listed (permissions, a drive offline) or the notebook has too many files: a name can't be known to be the only one. A folder that raced away is not one of these.
- **Warning.** There is no fingerprint: a different file with the same name gets the records. The dialog says so and shows every pair before anything is written.
- **Apply (on confirmation).** The plan is made again and refused if it differs from the one shown (a token). Side files and the Python code move as in an in-app move, but never over what the file found already has (the destination is created exclusively, so a side file the app saves there meanwhile is kept and the old one stays, and is reported; a pair of which nothing moved for that reason is not listed as moved, and a pair that fails stops only itself; set-aside side files are written exclusively too, then their record is removed, and the next plan only pairs what is left); an open note whose review was replaced reloads it (`REVIEWS_MOVED_EVENT`), and a review client whose review id is gone loads the path's review instead; then review comments (an empty review at the new path gives way; one that gained comments since keeps them, and the moved review stays where it was), stars and tags, reference attachments and the tethered `.bib` follow in one write per store (the migration's batch helpers), and Global Search is told. Markdown links are not rewritten, as for every move in the app (`docs/features/related-notebooks.md`); the check run after the fix still lists them. Not for shared notebooks, nor while a migration involving the notebook is unfinished, about to start, or an unreadable journal might involve it: the apply runs as a notebook operation (`withNotebookOperation` in `migration-fence.ts`), so a migration cannot start in the middle of it.

A recording's transcript is kept when the recording is missing (the tree's upkeep, `pruneAudioSidecars`, drops only its waveform), so a recording moved in Finder gets it back. The waveform goes only when nothing at the path is a file (a folder there does not count as the recording) and the path is looked at again right before it is removed, so a recording a sync client puts back keeps it. Tests: `scripts/editor/notebook-repair.test.ts`.

## Acknowledge: removing what is stale

After Try to fix has found what it can, **Acknowledge…** removes what the check still reports as stale, so that checking again lists only what needs you (`src/lib/storage/cleanup.ts`, `src/app/api/notebooks/cleanup/route.ts`). The check marks each finding it can clear with `clear` (the actions that remove it), so the two always agree on what is stale:

- what is left of files that are gone: their side files, side files set aside in case they come back, a note's Python code, stars, tags, review comments, the agent's changes waiting for review, reference attachments, a tether to a missing `.bib`;
- side files saved for another version of a file that is still there (definitions, outlines, transcripts; for ink, only the ink files drawn on another version, the pages drawn on this one stay), ink files of pages the file doesn't have, images no note shows (annotations and comments saved for another version are listed, never offered: they are people's work on a file that may differ only a little);
- out-of-date caches, the citation index and the `.bib` mirror.

Never stale, by the same name rule as Try to fix: an image no note shows whose file name a note's missing embed has (probably that embed's image, left behind when a folder moved), Python code named like a note that has no code of its own, side files of a file that can't be checked (no permission, a drive offline), and side files set aside for a file that is back (same bytes, or back under its old path), ink included; these stay listed, with what to do.

Also left out, and counted as remaining (the plan says why in `notes`): records of a path that Try to fix could not pair only because several files have its file's name (`several`, `shared-name`, `own`: after a folder rename in Finder, repeated names like `notes.md` may belong to one of them), set-aside side files of such a path included; and everything a check found that ran only in part (`incomplete` or `failed`), since a partly run check can't tell what is stale (its protection of set-aside files whose file came back may not have run). Both plan and apply filter the same way, so the token agrees. Records of a file moved to *another notebook* in Finder are not protected: names are not matched across notebooks. The refusal while Try to fix can still move records names the pairs.

Some of this is what people made. The dialog lists every item with what removing it costs, marks what is deleted for good (annotations, ink, comments, transcripts, code, images, pending agent changes), and when there is any, the remove button waits for **I understand these are deleted for good**. Acknowledge is refused while Try to fix can still give a moved file its records back, so they are never deleted instead of moved. Applying runs the check again and is refused if what it would remove changed (a token: each action names exactly what it removes, an attachment by its library and reference, the tether by its target, and the version of every file or review it would remove: size and time, the review’s content). Each removal is decided again right before it, and anything that can no longer be shown stale and unchanged is **held**, not removed:

- **Version.** A file saved at the same address since the plan (new ink, a newer transcript, a review with a newer comment) is another version and is kept; the review is compared and removed in one transaction (`deleteReviewKey`).
- **Gone, decided as the check decides it.** The file whose absence made a record stale is gone when its exact name is not a file in its folder’s listing (`fileExistence`), the same in plan and apply. A name a disk opens as a file spelled differently (letter case, Unicode form) is that file’s, so its records are left out of the plan, and a folder where the file was does not hold its records back. Set-aside side files are held when the file they were kept for is back under its old path, checked at deletion too. A set-aside ink folder goes as one unit: its payload first, its record (which says whose ink it is) last and only if all of the payload went.
- **Images** are also looked for in every notebook’s notes by address (`/api/files/raw/...`, and `/api/markdown-assets/raw?document=` naming a note of another notebook), as ordinary asset pruning does; when those notes can’t all be read, no image is offered. At apply, the notes are read again just before the images are removed (images go last), so one a note shows since is kept. A draft that is open and unsaved is not asked about (nothing in the dialog can reach the editors’ drafts); the dialog warns that a note not yet saved loses its image.
- **The tether** is compared and removed under its own lock (`untetherBibFile` with a check), and only when its file is known to be missing from a folder that can be read: an unreadable folder (or one that isn’t there, which may be a drive not connected) keeps it.

Nothing is deleted whose folder, once links and junctions are followed, is outside the notebook or its system folder. A review is deleted for its exact path, an attachment from its one reference. The result counts what was **removed**, **already absent**, **unreadable** (could not be checked or removed) and **held**; only the first two count as done, so a finding whose removal did not happen stays and is reported. The dialog lists, under each item, every concrete record (path) and the file it was kept for, the first five and a “Show all” for more. It then refreshes the tree, whose upkeep moves side files to files found again and brings the link index up to date, before checking again. Not stale, and left listed: broken links, missing images and LaTeX files, unreadable or damaged files, records a reader drops, agent undo history, unfinished migrations and the settings file. Not for shared notebooks. Like Try to fix, the apply is a notebook operation: refused while a migration involves the notebook, is about to start, or an unreadable journal might, and a migration cannot start while it runs; the tree's upkeep is skipped on the same terms. Tests: `scripts/editor/notebook-cleanup.test.ts`.

## Moving files in the app

Moving, renaming or archiving a file (`moveFileToDirectory`, `moveFile`, `archiveFile`, and the folder renames and archives in `src/lib/storage/files.ts`) keeps everything that points at its path pointing at it, so a check afterwards finds nothing at the old one:

- **Pending agent reviews** are written at the new path before the file moves and removed from the old one after (`withMovedReview`, `withMovedReviewsUnder` for a folder), so the review is never only at a path whose file is missing. A note moved to another notebook gets its image rewrites, and its cited-key rewrites once `copyCitedReferences` has run, applied to the review's baseline.
- **Undo history** follows through `recordMovedRunFiles` (`recordMovedRunFolder` for a folder), with the same rewrites and the file's hash before and after them.
- **Leftover records at the destination** refuse the move (409, naming what is kept and pointing here): side files other than caches, review comments, pending agent changes, a star or tags, a reference attachment, kept for a file deleted outside the app. They would be destroyed or handed to the moving file. Caches and an empty review (the one opening a note makes, which the moving file's review replaces) don't count. Check Notebook, then Try to fix or Acknowledge, clears them. Annotations kept in an older layout (keyed by file name alone, in a flat file or a dot file) count too when the migrator would give them to the arriving file, that is when no other file of the notebook has its name (`legacyAnnotationSidecars`, read only, on the migrator's matching rules; the moving file itself is not a rival, and with the same name the notes are its own or ambiguous). A notebook that can't be listed is not shown to be free of them.
- **Folder moves** (`renameFolder`, `archiveFolder`) scan the folder's notes before anything moves; a child that can't be listed, or more than 20,000 entries, refuses (409) instead of moving the folder and stranding the code of the notes not seen. The destination check includes Python code already at the paths the notes will take (an archive picks another name instead), and code never replaces code. If a later step fails, only the transfers that completed are taken back, so records that arrived at the destination meanwhile are never taken to the source; a take-back that can't finish is reported with what is stuck (500).
- **Deleting a folder** reads every note in it first and refuses (409) before deleting anything when one can't be read; its Python code and images are then cleaned up from that inventory. If the rest of the notebook can't be read in full to check that no other note uses the images, the folder is still deleted but the error says its images were left behind.
- **Record stores** (`scripts/editor/notebook-record-stores.test.ts`): stars, tags and the panel's expanded folders are written through one queue (`updateWorkspaceMetadata`), so a move's rekey and another save never erase each other. The destination of a pending agent review is checked inside the locks that cover its write and rollback, and a folder move checks all of them before writing any (409). An empty review at the destination gives way only to a review that really is at the source. Deleting a file or folder (`discardReviewsAt`, `discardReviewsUnder`) removes its pending agent reviews; listing pending reviews never drops the baseline of a file it can't find (a note moved outside the app stays for Try to fix), only a baseline back at its file's text. A review index that can't be read stops Archive File, Archive Folder and the migration plan with an error before any free name is looked for (`reviewIndexBlocker`).
- **A change of file type** (rename to another extension) is refused when the file has records the new type cannot keep: a kind it has no use for, or ink whose chunks the new type's editor never shows (a PDF's pages against an image's single chunk or a note's blocks; `inkChunksTheTypeLacks`). Bytes are not converted; only caches are dropped.
- **Nothing that arrives is replaced.** The note and its records (annotations, outline, definitions, transcript, ink, Python code) are published without replacement (`moveFileWithoutReplacing`, `moveWithoutReplacing`): a file or record that appears at the destination after the check refuses the move (409), and what already moved goes back, only to a place that is still free. A case-only rename (`Paper.md` to `paper.md`) is the one move that renames over its destination, and only after confirming again that both spellings are one file (same device and inode).
- **Archive is a move.** It picks its archive name, then takes the same checks, commit and rollback as Move (`performFileMove`), so a record that can't follow (a file where its folder would be) leaves the file where it was.
- **The file you chose is the file that moves.** A move, archive or delete may carry `fileId` (`localFileIdentity` of the tree node: when it was created and its size); a path that holds another file by then is refused (409, "changed since it was read"). Whatever the request carried, the file is looked at again right before it moves and refused if it is no longer the one the move began with. A delete checks the identity at the route only; its own record handling is `deleteFile`'s.
- **A save and a move of one file never interleave.** Both hold the path's lock (`withPathLocks`); a save publishes only while the file still holds what it just read (`replaceFileIfUnchanged`), and refuses a file that is gone or was replaced instead of recreating or overwriting it.
- **After the file moved, nothing fails the request.** The records follow one by one; a step that fails (the star, the review, the attachments, the history, the images) or a review held at the old path because the destination gained comments is reported in the response: `moved` (`from`, `to`) and `unfinished` (`step`, `status`, `message`) next to the usual file payload. If only reading the result fails, the error body carries the same two fields. Check Notebook, then Try to fix, pairs what stayed behind by name.
- **Other notebooks.** `PATCH /api/files` does not take a move to another local notebook (409): that is the migration's (reviewed, crash safe, with its references), which the Move menu and drag and drop open (`moveFileToFolder`).
- **Drag and drop to another notebook** opens the migration dialog like the Move menu does (`moveFileToFolder`).

Tests: `scripts/editor/notebook-move-integrity.test.ts`.

### Copies and shared writes

- **A copy takes a free name** (`findAvailableCopyPath`): no file there, and none of the records a file deleted outside the app left (`destinationRecords`), so a copy never inherits or replaces them; its own records are published exclusively. A name that holds records is skipped like a taken one (`copy-1.md`).
- **A copy keeps the file type** (`assertCopyKeepsType`): its bytes, records and viewer follow the source, so another extension is refused (400). Changing type is a rename, which checks what the records can keep.
- **A note copied to another notebook** runs `copyCitedReferences` like a move: cited references are copied or mapped, the copy's text is rewritten, and the copied review's snapshot follows the same key map. The result carries `references`.
- **Copying shared text** reads the host's current text. Only when there is no shared authority (collaboration off here, notebook not joined) is the disk copy used; a host that cannot answer refuses the copy.
- **Shared moves** (`moveSharedFile`, `renameSharedFolder`) check the records this computer keeps at the destination before the host moves anything, as a local move does (409). Once the host has moved, every step runs and a record that could not follow is reported (500, Check Notebook settles it).
- **Shared deletes** (`deleteSharedFile`, `deleteSharedFolder`) remove the records kept here after the host's deletion, as a local delete does: sidecars, review comments, reference attachments, stars and tags; failures are reported.

Tests: `scripts/editor/notebook-operations-integrity.test.ts` (copy), `scripts/editor/notebook-shared-move-integrity.test.ts`.

## Bounds, progress and stopping

A check runs under limits (`DEFAULT_INTEGRITY_LIMITS`: 20,000 entries, 64 MB read, 30 s, 10,000 findings); reaching one makes the checks it cut short partial, saying which limit. The budget is asked at every entry of the walks, before each file is read (the size is taken first, so a file the limit can't hold is never read, and the raw bytes read are counted), and between the chunks of a hash; a check is not started once the budget is gone (it is reported as stopped at the limit). When the file listing was cut or a folder could not be listed, the checks that depend on it (side files of files that are gone, Python code and its owners) are partial and offer nothing for Acknowledge to delete: a side file that could not be read or a candidate that could not be hashed holds back the same way. The report carries what the check cost (`statistics`) and its `completeness`. With `?stream=1` the route sends newline-delimited JSON: one `progress` line as each check starts, then the `report` (or an `error`). The dialog shows the check it is on and a **Stop** button; stopping, closing the dialog or the request going away aborts the check between reads, hash chunks and directory entries (a request that is already gone aborts it before it starts). Not yet under the budget: the owners' own readers (`listSidecars`, ink folders, `readOrphans`), the LaTeX source reads and the `_assets` walk.

## Read only

Read-only means no maintenance-capable path is used: not the tree load, not the review store's migrating reader, not the reference library's quarantine, not the readers that upgrade older annotation or ink layouts. Finding where a linked folder is reads its state without its upgrades (and holds its location to the same marker proof as the app does): `verifyNotebook` runs under `withReadOnlyStorage` (paths.ts), under which `readDirectoryModeState` (electron/directory-mode.cjs) neither rewrites an older state file nor writes a folder's identity marker nor records its location. The search index is opened read-only, and only when that creates nothing (a WAL index needs its shared-memory file to exist already); otherwise it is skipped.

Two tests hold this: one snapshots the whole data folder before and after a check; the other replaces every writing call of `fs` and `fs/promises` (and opening for writing) while checking a notebook with every kind of side file, indexes, a mirror and a linked folder in an older state file without its marker, and fails on any call.

## As a test oracle

`scripts/editor/notebook-test-helpers.ts` exports `assertNotebookSound(notebook)`, which runs this check and fails on any error or warning not explicitly expected. The migration tests assert it after every scenario, and `notebook-operations-integrity.test.ts` runs the everyday file operations (move, rename, archive, copy, delete, folder operations, moves between notebooks) on a notebook seeded with every kind of side file, a star, tags and a reference attachment, asserting each leaves both notebooks sound, notes included (except the link and citation indexes' lag, which the app's next tree load clears and the sweep deliberately never runs). It found that a note that stays and shows a moving image by its library address breaks without warning; the migration review now warns about it.

The migration's final check uses `checkNothingLeftAt` from the same module, so "nothing was left behind" means the same thing in both places: nothing at the old path, none of its side files, and no star, tag, review, pending agent change, reference attachment, tether or set-aside side file still naming it. A place or a store that can't be read is "unverified", never clean. The migration review reuses the same link and LaTeX helpers.

## Not checked

- Shared notebooks are checked as they are on this computer, not against the collaboration host, which keeps their files in step.
- A side file is compared with its file by size; a change that keeps the size is found by its owner when the file is opened.
- A same-path replacement of an image or note is not found where its records are keyed by path alone (image annotations record no source; stars, tags, comments and attachments are checked only for the path's existence). Telling a replacement from an edit would need an identity those records do not keep; it is left for a design of its own. A PDF's annotations saved before they recorded their PDF's identity get it in the background only when the PDF has not changed since the notes were last saved: otherwise the PDF's current bytes say nothing about what the notes were made for, and they stay without one.
- Links into other notebooks and LaTeX paths outside the notebook are not judged; a link's line in a text file is not checked.
- LaTeX names that need a macro are counted, not resolved, and `\usepackage` and `\documentclass` names are not checked.
- A ```chart block's data file is checked; ```html live blocks and ```mermaid diagrams are not: a live block runs in a sandboxed frame that can't read notebook files (only https or data: URLs load), and Mermaid runs in strict mode with no file references.
- Global Search is skipped when its index can't be opened without creating files (no one has it open).
