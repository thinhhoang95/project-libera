### C1. Temporary writer lease lapse invokes `followManifest()`, wiping `this.state.layout` hashes, stats, and version history
- **Files:** [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L509-L511), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L1052-L1056), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L1283-L1323), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L1521-L1527), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L1967-L1991), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L2343-L2347); [service.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/service.ts#L844-L850), [service.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/service.ts#L1067-L1071)
- **Root cause:**
  - `SharedProject.follower` returns `true` whenever `canWriteDisk(projectId)` is `false` (including when a writer's lease has temporarily lapsed while `handle.writer` is still `true`).
  - If `applyManifestPass()` runs during that lapse (e.g., WebSocket reconnects before HTTP lease renewal completes, or an explicit UI fileOp runs), line 1052 calls `this.followManifest()`.
  - `followManifest()` rebuilds `this.state.layout` from scratch with **no `hash`, `size`, `mtimeMs`, or `previous` hashes** (lines 1289–1293, 1318), unconditionally overwriting `this.state.layout` (even when zero manifest entries changed, because `JSON.stringify(previous) !== JSON.stringify(next)`). It also updates moved paths and drops removed entries from `this.state.layout` without touching disk.
  - When the lease is renewed (`service.ts:846–850`), `writer === handle.writer`, so `switchRole` is **not** called; `leaseConfirmed()` only schedules a scan if `scanDeferred` (never `scheduleManifest(0)`).
- **Failure scenario:**
  1. Writer laptop sleeps or loses Wi-Fi for > 60s (`leaseDeadline <= performance.now()`).
  2. On reconnect, WebSocket catches up and triggers `applyManifestPass()` slightly before HTTP `acquireFolderLease` finishes -> `followManifest()` wipes all `hash`, `size`, `mtimeMs`, and `previous` fields across the entire notebook.
  3. Lease renews 200ms later; `this.follower` returns to `false`.
  4. `scan()` skips every file with `!record.hash` (`project.ts:2661`), blinding the scanner until a manifest pass runs.
  5. On the next `materializeDoc`/`placeBlob`, any text document or binary modified locally or remotely sees `!record.hash`: instead of running 3-way reconciliation (`project.ts:1967`), it executes `this.displacedPath(..., await this.archive(...))` (`project.ts:1985`, `1525`), **archiving the working file and migrating its annotations, tags, and sidecars into `_archive/`**. Files deleted or renamed remotely during the lapse are already dropped/renamed in `this.state.layout`, so they are never archived or moved on disk. `previous` history is wiped, breaking stale-copy and OneDrive conflict-copy detection.
- **Fix direction:** Distinguish permanent follower mode (`this.info.follower === true`) from a temporarily lapsed writer lease (`!this.info.follower && this.follower`). While a writer's lease is lapsed, pause `applyManifestPass()` (and set a `manifestDeferred` flag drained by `leaseConfirmed()` along with `scheduleWrite` for dirty docs) instead of executing `followManifest()` against the writer's `this.state.layout`.

### C2. Dual-writer split-brain across system sleep/wake on macOS and Linux
- **Files:** [service.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/service.ts#L598-L607), [service.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/service.ts#L1067-L1071), [service.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/service.ts#L1244-L1249); [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L2337-L2340)
- **Root cause:**
  - `lease()` computes `handle.leaseDeadline = requestedAt + Math.min(this.leaseTtlMs, grantedMs)` using `performance.now()`. On macOS (`mach_absolute_time`) and Linux (`CLOCK_MONOTONIC`), `performance.now()` **freezes during system sleep/suspend**.
  - `resumed()` (`service.ts:1244–1249`) does **not** zero `handle.leaseDeadline`, yet immediately calls `handle.runtime?.resumed()` (`scheduleScan(0)`) concurrently with `void this.tick()`.
- **Failure scenario:**
  1. Device A renews a 60s lease, then sleeps 5s later for 10 minutes.
  2. Server expires Device A's lease after 60s; Device B takes over the writer lease and writes to the OneDrive folder.
  3. Device A wakes. `performance.now()` still shows 55s remaining on `leaseDeadline`. `canWriteDisk()` returns `true` and `keepsWriting()` returns `true` even if Wi-Fi is still reconnecting (`unavailable`).
  4. Device A runs a full disk scan, materializes files, and writes `state.json` concurrently with Device B for up to 55 seconds, causing OneDrive conflict copies and `state.json` clobbering.
- **Fix direction:** In `resumed()`, immediately zero `handle.leaseDeadline = 0` for all handles before invoking `tick()` and `runtime.resumed()`. Also track `(wallClock, monotonicClock)` pairs on lease grant/check and invalidate `leaseDeadline` if wall-clock elapsed time minus monotonic elapsed time exceeds a small jump threshold (catching undetected sleep events).

### C3. Permanent notebook/album deadlock on a second device when taken down while that device was offline
- **Files:** [service.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/service.ts#L464-L472), [service.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/service.ts#L781-L805); [shared-notebook.ts](file:///Users/thinhhoang/Documents/project-libera/src/lib/collab/shared-notebook.ts#L85-L110); [gallery-sharing.ts](file:///Users/thinhhoang/Documents/project-libera/src/lib/storage/gallery-sharing.ts#L50-L59); [local-notebook-state.ts](file:///Users/thinhhoang/Documents/project-libera/src/lib/collab/local-notebook-state.ts#L53-L107)
- **Root cause:**
  - When a stored project's folder exists on disk without `.libera-shared.json`, `loadStoredProjects()` calls `repairMissingMarker()` and skips starting a runtime.
  - `repairMissingMarker()` (`service.ts:797–798`) collapses a definitive server `404` (`api.getProject(projectId).catch(() => null)`) into `return false` without recording `"local"`/`"revoked"` in `notebook-lifecycle` or deleting the SQLite project row.
  - Because `SharedProject` never opens, `hostEvent()` ignores the project, `tick()` skips it, and `adoptMarkers()` ignores the markerless folder.
  - Meanwhile, Next's `effectiveMarker(root, null)` (`shared-notebook.ts:87–89`) sees the active `binding-<hash>.json` with `readNotebookLifecycle === null` and permanently returns `UNREADABLE` (`projectId: ""`), blocking every local write (`409 shared-document`) and every shared write (`400 not-shared`).

- **Fix direction:** In `repairMissingMarker()`, distinguish `404` from transient network failures. ### C4. `createFromDisk()` mutates `this.state.layout` before manifest publication; abort or disconnect causes `applyManifestPass()` to archive/delete the brand-new file
- **Files:** [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L3216-L3255), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L3560-L3586), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L1698-L1704), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L1094-L1103), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L1589-L1605)
- **Root cause:**

- **Failure scenario:**

  2. During `createFromDisk()`'s HTTP upload, the WebSocket reconnects (`manifestCaughtUp()` becomes `false`).

### C5. Owner takedown (`prepareLocalConversion`) can silently lose latest text, PDF marks, and PDF comments before deleting the server project
- **Files:** [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L656-L696), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L705-L768), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L820-L833); [pdf-marks.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/pdf-marks.ts#L513-L516), [pdf-marks.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/pdf-marks.ts#L568-L580), [pdf-marks.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/pdf-marks.ts#L629-L640); [pdf-comments.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/pdf-comments.ts#L159-L181)
- **Root cause:** Four compounding defects in the takedown barrier:
  1. **Stale doc set & omitted unready docs in `catchUpWithFence`:** `prepareLocalConversion` holds the project queue while `beginFence()` freezes the server and `catchUpWithFence` waits on `manifest`. Because `applyManifest`/`followManifest` cannot run while the queue is held, any text doc added or renamed right before the fence is missing/stale in `this.state.layout` and `this.docs`. Worse, line 824 filters `...[...this.docs.values()].filter((doc) => this.docReady(doc))`, silently omitting any doc whose hub isn't ready yet.
  2. **Stale layout & swallowed errors in `preserveLatestText`:** `preserveLatestText()` iterates stale `this.state.layout` (not post-fence `entries`/`layout`), skips `!runtime || !this.docReady(runtime)`, and **catches and swallows** `WriteCancelledError` (including `SLOW_READ` on a OneDrive cloud file at line 668), `PathRefusedError`, and `ENOENT` instead of aborting takedown.
  3. **Unopened live PDFs skipped:** `catchUpWithFence` only waits on `this.pdfs.openDocIds()`, and `exportLocal()` only exports `[...this.docs.values()]`. Any PDF in `fence.docs` whose hub wasn't opened on this device (e.g., startup `refreshServerDocuments()` failed transiently or a `PdfDocumentCreated` event was missed/still in flight) loses all its Yjs PDF highlights/marks permanently when the server deletes the project.
  4. **Corrupt sidecar & fake `strict` comment export:** `writeCurrentCopy` (`pdf-marks.ts:515`) calls unguarded `JSON.parse`, aborting takedown (or silently dropping marks on revocation). - **Fix direction:** After `manifest` catches up to `fence`, derive the exact post-fence entries/layout, ensure every text doc and every `kind === "pdf"` doc in `fence.docs` is acquired/opened, wait for **all** of them to reach `fence`'s `serverSeq`, run a strict text export iterating post-fence `layout` that throws on any skipped/unready/failed doc, wrap `JSON.parse` on existing sidecars with quarantine fallback, pass a strict-mode flag (or direct `api.listThreads`) into `commentsForCopy`, and require an active `closing_at` fence on server `DELETE /v1/projects/:id` whenever `recovery` or `expectedManifestSeq` is supplied.

### C6. `DocHub.handleReject()` wipes preserved local text to empty on mid-flight access revocation, document deletion, or transient `not-open`
- **Files:** [doc-hub.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/core/doc-hub.ts#L911-L955), [doc-hub.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/core/doc-hub.ts#L987-L1032); [outbound.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/core/outbound.ts#L285-L295); [server.ts](file:///Users/thinhhoang/Documents/project-libera/server/src/sync/server.ts#L330-L337), [server.ts](file:///Users/thinhhoang/Documents/project-libera/server/src/sync/server.ts#L449)
- **Root cause:**
  - When access is revoked or a document is deleted mid-flight, the server sends `Closed("access-revoked")` **and** `Reject(reason: "not-open")` (`server.ts:335–336`), or `Reject(reason: "not-open", "The document was deleted.")` (`server.ts:449`).
  - `Closed` calls `stopSyncing()` -> `outbound.stop()`, which keeps `this.batches` intact.
  - `handleReject()` (`doc-hub.ts:911–914`) checks neither `this.meta.readOnlyReason` nor `message.reason === "not-open"`. Because `hasBatch(clientSeq)` is still `true`, it runs `rollback()`, executing `store.wipeSubdoc()`, replacing the live `Y.Doc` with an empty `Y.Doc`, broadcasting empty state, and calling `this.link?.reopen()` — which is a no-op because `canSync()` is `false`.
- **Failure scenario:**
  1. User edits `docA` while an update batch (`clientSeq = 5`) is in flight; owner revokes access or deletes `docA`.
  2. `Closed` marks `docA` read-only (`access-revoked` / `document-deleted`) to preserve local text for recovery/export.

Subsequent `preserveLatestText()` or read-only viewer sees blank content. Similarly, a transient `room.disposed` `Reject("not-open")` (`server.ts:331`) wipes valid local edits instead of reopening and resending.
- **Fix direction:** In `handleReject()`: (1) ignore rejects when `this.meta.readOnlyReason === "access-revoked" || this.meta.readOnlyReason === "document-deleted"`, and (2) treat `reason === "not-open"` as a transient reopen trigger (`this.outbound.stop(); this.link?.reopen();` if `canSync()`) rather than a destructive `rollback()`.

### C7. Delete-only server diffs in `applyServerUpdate()` mutate memory before SQLite commit, causing permanent loss on restart after transient persist failure
- **Files:** [doc-hub.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/core/doc-hub.ts#L664-L674), [doc-hub.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/core/doc-hub.ts#L727-L769), [doc-hub.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/core/doc-hub.ts#L858-L876), [doc-hub.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/core/doc-hub.ts#L887-L901)
- **Root cause:**
  - For delete-only `Opened` diffs (`!hasStructs(diff)`), `applyServerUpdate()` calls `Y.applyUpdate(doc, diff, { kind: "server", serverSeq, persistEffective: true })`.
  - Inside `onDocUpdate()`, `persistAcked()` runs **after** `Y.applyUpdate` has already mutated the in-memory `Y.Doc`. On a transient SQLite failure, `onDocUpdate()` catches the throw (setting `resyncPending = true`) and still broadcasts the unpersisted deletion.
- **Failure scenario:**
  1. `Opened` delivers a delete-only diff; `Y.applyUpdate` mutates `doc` in memory; `persistAcked()` throws transiently (`SQLITE_BUSY` / disk full).
  2. `resyncTimer` reopens the doc. Server sends the exact same delete-only diff.

  4. `persistAcked()` is never called; `processOpened()` advances `last_seen_server_seq` and marks `caughtUp = true`.

- **Fix direction:** Probe whether the delete-only diff actually changes state on a scratch/diff check or compare `Y.encodeStateAsUpdate` / delete-set membership **before** applying to the live `Y.Doc`, and persist via `persistAcked()` **before** `Y.applyUpdate(doc, diff, { persistEffective: false })` (matching the `hasStructs(diff)` path).

### C8. Blobs treat `isUncertainCopy` identically to `isStaleCopy`, reverting legitimate replacements/reverts and `fs.rm`-deleting photos in shared albums
- **Files:** [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L2766-L2775), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L1521-L1527), [project.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/project.ts#L1589-L1605); [state.ts](file:///Users/thinhhoang/Documents/project-libera/electron/collab/notebooks/state.ts#L96-L106)
- **Root cause:**
  - `isUncertainCopy(record, hash, mtimeMs)` returns `true` for any file whose hash appears in `record.previous` (even with a brand-new `mtimeMs > record.mtimeMs`) **or** whose `mtimeMs <= record.mtimeMs` (any copied/extracted file preserving an older mtime, or same-tick write on FAT/ExFAT).
  - Unlike text documents (which open a reconciliation for `isUncertainCopy`), line 2769 treats `isUncertainCopy` identically to `isStaleCopy` for blobs, calling `placeBlob()` -> `archive()` -> overwriting disk with the old blob.
  - In shared albums (`this.info.album === true`), `archive()` executes `fs.rm(source, { recursive: true, force: true })` (line 1599).
- **Failure scenario:**
  1. **Shared album (permanent deletion):** User copies an updated `photo.jpg` from their camera/Downloads (keeping its older camera mtime) or reverts `photo.jpg` to a previous version. `isUncertainCopy` fires -> `placeBlob` -> `archive()` **`fs.rm`s the user's new photo permanently** and puts the old blob back.

- **Fix direction:** Only auto-revert blobs on strict `isStaleCopy` (matching both an earlier hash **and** its recorded mtime within `MTIME_SLACK_MS`). For `isUncertainCopy` with a **newer** `mtimeMs` (intentional revert to a previous hash) or a **new** hash with older mtime (copied replacement whose `ctimeMs` moved after `record.mtimeMs`), treat as a legitimate replacement (or surface a user confirmation/conflict instead of silently overwriting and `fs.rm`-deleting in albums).
